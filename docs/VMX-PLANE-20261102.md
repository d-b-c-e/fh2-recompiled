## Independent comparison

`windows/tools/fh2_vmx_plane_check.py` reuses the existing closed camera fixture.
It independently decodes 25 original instruction words from the pinned image,
rather than taking register operands from generated disassembly comments.
The decoded kernel covers four checked near-corner loads, eight immediate
permutations, vector multiplies/copies and four negative multiply-subtracts.

The scalar evaluator keeps architectural XYZ/W order and imports no SDK vector
types, shuffle intrinsics or generated arithmetic. The private compiled
constructor records 16 intermediate vectors: four loaded corners, eight
permutation results and four cross-product results. The generator inserts
observations only into that private fixture; it changes no native game source,
register state, guest memory semantics or deployed executable.

The VMX128 field layout and permutation convention are cross-checked against
[Xenia's decoder](https://github.com/xenia-project/xenia/blob/95a5c3ee250f80c3b9d139658649d9ffb6db3eec/src/xenia/cpu/ppc/ppc_instr.h)
and [VMX emitter](https://github.com/xenia-project/xenia/blob/95a5c3ee250f80c3b9d139658649d9ffb6db3eec/src/xenia/cpu/ppc/ppc_emit_altivec.cc).
The [AltiVec Programming Interface Manual](https://www.nxp.com/docs/en/reference-manual/ALTIVECPIM.pdf)
specifies the negative multiply-subtract operation. These are documentation
cross-checks, not execution on original hardware.

- Immediate 135 selects `(Z,X,Y,W)`; 99 selects `(Y,Z,X,W)`.
- Standard VA fields B/C are decoded independently: B is the addend, C the
  second multiplicand. The operation is `-(A*C-B)`. The actual generated
  calls use those operands in the same roles.
- SDK vector loads reverse all 16 bytes. Consequently guest X is host float
  lane 3. The observer reverses the four host lanes back to XYZ/W before
  comparison; this agrees with the eight permutation observations.
- Each case compares 64 intermediate components plus 16 normalized side-plane
  components: 80 * 12 = **960**. Maximum recorded intermediate absolute
  difference is `3.8418579428878274e-9`, including decimal output round trips.
- Absolute tolerance is `1e-7`, relative tolerance `2e-6`. Reciprocal-square-root
  estimate bits, fusion corner cases, exceptional inputs and signed-zero bits
  are not independently qualified. Both existing FP policies are exercised.

Sensitivity controls detect a changed permutation lane and a swapped
multiply-subtract addend/multiplicand. Wrong-image input refuses before output
creation or compilation. The original **368** ordering/cache/projection
assertions still pass; none was weakened or removed.

## Why this does not clear culling

For an identity pose with conventional ordered extents L<R, B<T and near n>0,
the four normalized side directions reproduce these unnormalized directions:

| Stored side | Direction before normalization |
| --- | --- |
| Left | `(n, 0, -L)` |
| Right | `(-n, 0, R)` |
| Top | `(0, -n, T)` |
| Bottom | `(0, n, -B)` |

With the tested L=.4n, R=1.6n, T=.6n, B=-.6n, the actual plane-test acceptance
halfspaces require x<=.4z and x>=1.6z, as well as y>=.6z and y<=-.6z. This
explains the positive-Z rejection already observed. Those directions follow
the decoded original cross products as well as the generated SIMD path.
This does not establish a defect in the original game: the real kind-1
producer convention and receiver/view pairing remain unknown.

The comparison is deliberately limited to this finite corner/cross-product
kernel and identity-pose side planes. It does not independently qualify the
entire constructor, matrix inverse, near/far construction, full ISA behavior,
original hardware or rendered culling. The tool retains exit 2 and the owned
receipt remains failed because the existing culling assertion is held.

kind field +8 and sets dirty 480. Thus slot 48 is not the only possible way
to select kind 1. Deferred slot 32 (`82F44BB0`) copies a word at payload +4;
callback `82F44B98` loads the word and tail-calls concrete slot 32.

The extended `fh2_extent_trace.py` verifies those paths and base/refcounted
slot identities: **45 static checks pass** over the same 85,237 functions.
No direct caller of the concrete/deferred kind setters was found. A bounded
backward argument scan finds seven constant-1 virtual-32 sites in six
functions, with receiver identity still unproved:

`831CA938` (two sites), `831349B8`, `82D4CB20`, `831CB410`, `83237BD8`,
`8293D7F0`.

Some sites pass extra pointer arguments or inspect return values inconsistent
with the concrete camera setter. The owner+4024 object in `82D4CB20` also
receives one/six floating-point arguments at slots 152/156, where the camera
has byte setters. A follow-up store scan finds initialization/destruction
writes, but no typed camera allocation for that field. These signatures do
not establish a camera receiver. Slot identity alone cannot classify them.
The next useful source task is to identify the object list in `8293D7F0` and
the incoming receiver of tail-wrapper `83237BD8`, then trace their allocation/
assignment before treating either as a camera selector.
Variable-kind calls, object aliases and copy paths remain possible. No actual
